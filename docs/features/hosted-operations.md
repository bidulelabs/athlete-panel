# Feature: Guided VPS operations

## Purpose and scope

Give a single owner a predictable installation, update and recovery workflow without host Node/pnpm, manual database URLs or knowledge of migration commands. Reuse Docker Compose, private PostgreSQL, Caddy and existing backup/domain protections.

Outside scope: provisioning a VPS/DNS/remote storage, executing a real publication or private-server deployment during implementation, unattended upgrades, automatic monthly restore scheduling, automatic deletion of old data, PostgreSQL major-version upgrades, and adoption of arbitrary or unsupported Compose topologies.

## Intended behavior

Specification status: approved within the request's scope.
Requirement source: the owner requested implementation of the five VPS installation/upgrade/backup/recovery improvements on 2026-10-25, including documentation and isolated tests, without publication or changes to the running instance. The owner subsequently requested image-based installation/upgrades with migrations, backups, recovery and custom plugins preserved. No durable conversation link is available; the [execution record](../plans/mvp-execution.md) preserves that statement.

On 2026-10-29 the owner explicitly approved implementation of the simplified deployment/recovery plan against `220a68a`: one backup scheduler with optional external heartbeat, application services updated together, removal of redundant archive authentication/post-upgrade backups, and extension of existing CI. Full pre-deployment restore rehearsal remains mandatory. See [ADR 012](../decisions/012-deployment-recovery.md) and the [implementation record](../plans/deployment-recovery.md).

The same day, the owner authorized GitHub release-tag protection and immutability, then requested the release-script update directly in PR 54: feature-branch beta releases and stable releases from main, without a permanent development branch. Actual image publication and server deployment remain separate actions.

- Installation generates separate technical secrets, prompts for the owner password, starts the production topology and verifies TLS, worker readiness and a backup. Existing credentials/data are preserved.
- Operator state stays private and outside source. Commands use a lock and durable checkpoints, not an always-running privileged updater. Image pulls/builds, plugin-preservation checks and retained-migration validation precede maintenance. A source-free release bundle pins a registry digest; source/local images remain supported for custom code.
- Upgrade prepares the pinned image, creates an authenticated preparation snapshot and restores/migrates it in disposable isolated containers while normal use continues. Only after schema, saved-data, application and worker checks pass does it pause writes, drain mutations and create a second fresh verified recovery point. This final snapshot includes writes accepted during rehearsal. It then stops web/worker/backup together, runs candidate migrations/permissions and verifies the candidate before reopening. PostgreSQL and unchanged Caddy remain running. A failed phase remains visible and resumable. SQL rollback and post-commit permission failures have distinct messages.
- The existing backup container runs immediately at startup, then daily, retaining seven daily/four weekly archives. Its new attempt, matched to the release and startup run, is the first post-upgrade backup. Failure after reopening reports “application deployed, backup failed”; resume retries only that service. Creation and retention share a database lock. Successful authenticated read-back is trusted within an uninterrupted operation; resume and restoration authenticate recorded archives again.
- Optional private HTTPS success/failure heartbeat endpoints receive no application data. Delivery is bounded and sanitized state/logs remain local. A separate monitor detects missed daily signals, including a stopped server when the next signal becomes overdue. No second scheduler, hourly host monitor or monthly restore timer is introduced.
- On-demand `restore-test` uses the same rehearsal runner, its own database, labelled storage and an internal network without published ports. It receives no live database credentials; provider jobs stay paused in maintenance. Cleanup targets only that run's resources. A local test cannot prove recovery after losing the VPS or the availability of separately held keys.
- Existing CI builds one AMD64 image, checks its packaging, transfers a checksummed artifact to all three container rehearsals and preserves security scans. All prerequisites, including those unexpectedly skipped, must succeed. Version-tag/manual-tag publication uses that tested image without rebuilding, verifies the registry digest, and publishes a matching bundle/checksum/report. Only publication receives write permissions; retries preserve existing version contents. Commit identity is optional for older image/archive metadata and mandatory for CI releases.
- Tags with a prerelease suffix, including beta/rc, may identify feature-branch commits and publish as GitHub prereleases explicitly excluded from Latest. Stable tags require a commit reachable from freshly fetched main on every attempt. Both require the exact tag/package version and tested commit. Draft completion reapplies the appropriate classification; already-published mismatches fail without modifying the release. GitHub tag restrictions and release immutability are external controls, not permissions established by the script. Beta installation uses an explicitly selected independent test instance with synthetic data.
- Backups authenticate a read-back before becoming completed archives. Managed storage requires the expected network filesystem and identity marker; a missing mount cannot silently become a local directory. Off-host recovery is not claimed merely from an archive or marker.
- Recovery authenticates before changing the target, restores into a new database and source directory, selects the matching image or explicitly rebuilds authenticated source, restores grants and checks the restored application. The prior database is retained. Lost-server recovery uses separately recovered operator keys/state and the remote archive.
- Resuming does not replay committed migrations or reset an existing owner. Ambiguous interrupted restore targets remain preserved and require a new recovery attempt rather than destructive guessing.
- Candidate ingress is validated before replacing the live file. Reload intent is durably recorded before the write and retried after interruption until Caddy confirms it. A previous worker that cannot report a maintenance heartbeat within the bounded drain wait is stopped with a 30-second grace period; the final snapshot requires confirmed termination. Candidate-worker readiness still requires a fresh heartbeat.
- Public readiness requires a direct HTTP 200 response from the configured HTTPS `/api/health` endpoint, with JSON content type and an object containing `"status": "ready"`. Additional fields, including the existing synthetic-instance marker, remain valid. The controller verifies TLS, rejects redirects without following them and rejects malformed, unrelated or oversized responses before checking the fresh worker heartbeat.
- A retention failure does not invalidate an authenticated completed backup or cause deployment to retry it. `backupAttempt.retention` records the separate result, logs explain the warning, and the next daily run retries cleanup under the same coordination lock. The scheduled monitor receives a failure signal for retention errors; deliberate SIGINT/SIGTERM cancellation sends no failure signal. Local cancellation status and plaintext cleanup remain intact.
- Current images use the shared console data validator; older protocol-1 images retain a compatibility payload. Both paths are tested against invalid persisted data. Publication diagnostics identify the failing operation, exit code and a bounded failure category without exposing command arguments or raw remote output.

## Explicit adoption and portable identity

On 2026-10-30 the owner approved explicit adoption of supported manual Compose installations and portable Docker image verification. See [ADR 013](../decisions/013-compose-adoption-and-image-identity.md) and its [execution record](../plans/compose-adoption.md).

Adoption preview is read-only: inspect explicitly supplied project/context, ordered Compose overrides, environment files and service mappings; show a sanitized confirmation fingerprint. Confirmed adoption revalidates the same facts and writes private controller state only. It never restarts services, creates another instance, migrates, bootstraps an owner, rotates credentials, rewrites Compose inputs or changes backup protection. Retain the original image in a checksummed private archive, its source/plugin metadata, database/volume/network identities and configuration/key references. Write the versioned profile atomically; interrupted creation can be retried with the same state directory.

A local daemon/project ownership claim outside arbitrary state directories prevents duplicate controllers; a nonblocking lock coordinates operations. Revalidate referenced files, the effective model and runtime before upgrading. Changed customizations require explicit reconciliation, with a fresh preview/confirmation; database, key, volume, network and mapping replacements are blockers. Reconciliation never selects a different running release. The first adopted upgrade follows the full existing rehearsal, preparation snapshot, drained final snapshot, migrations/grants, public/fresh-worker readiness and matching scheduled backup sequence. Recovery restores a new database and retains the prior database, including recovery to the initially adopted release.

Missing application containers are recoverable only at stages that recreate them: explicit recovery before reopening, or upgrade resume after the final verified recovery snapshot. Once normal use has reopened, resume may recreate only backup and must verify its new matching startup attempt, even if an earlier backup succeeded. Initial adoption, ordinary upgrade preparation and restore tests still require the complete installation. Missing or duplicated database/ingress containers, changed persistent volumes/networks, configuration, keys or backup-storage identity remain blockers at every stage. Recreated bind mounts must already exist; Compose must not create empty replacement directories.

### Initial support matrix

| Area | Supported | Blocker / operator action |
| --- | --- | --- |
| Host | Linux, Python 3.10+, Docker Compose v2 and Buildx; explicit local Unix Docker context | Run on the Docker host; remote/SSH/TCP contexts and Swarm are unsupported |
| Database | One private PostgreSQL 17 service; official `postgres:17…` or `postgres@sha256:…` reference (also `docker.io/library/postgres`); running major version and selected/running image identity verified; one named volume or existing bind at `/var/lib/postgresql/data`; distinct admin/runtime users | External DBs, exposed database ports, image mismatches, major upgrades, extra data mounts and custom DB launch commands require a separate procedure |
| Services | Exactly one web, worker and existing backup-loop scheduler; admin/recovery console roles; backup/recovery explicitly use the controller UID; explicit role-to-name mapping | Flatten wrappers, replicas and unrelated services into a reviewed supported layout before adoption |
| Ingress | Existing Caddy service or externally owned HTTPS proxy; secure cookies and trusted client-IP header contract | Operator must establish HTTPS/header correctness; adoption does not change proxy configuration; preserve its separate recovery copy |
| Storage | Existing named volumes, bind storage, custom Docker networks; registered off-host backup policy and marker | Missing mounts/keys/policy fail; local/named-volume backups are not silently promoted to off-host protection |
| Secrets | Resolved environment values, explicit private env files, file-backed Compose secrets and `/run/secrets` binds | External secret managers and executable env/wrapper sources are unsupported; keep protected recovery copies |
| Custom code | Protocol-1 image containing plugins, source and retained migrations | Source mounts and custom entrypoints are unsupported; build trusted code into the image first |
| Compose inputs | Explicit ordered files/overrides and env-file paths; resolved model and referenced files tracked | `include`/`extends` indirection is outside this matrix; provide reviewed flattened inputs |
| Reconciliation | Same daemon/cluster/storage/mappings/keys; reviewed configuration matching running services | Restore original identities or use explicit recovery; no automatic replacement or credential rotation |

Registry index, platform manifest, configuration digest and local Docker ID are separate values. Exact-image verification proves their relationship and the selected platform; labels alone are insufficient. New artifact/bundle descriptors and authenticated backup metadata carry portable identity. Existing descriptors and archives remain readable; unknown legacy identifiers require proof, an original retained image or explicit authenticated-source rebuilding. Published releases are never rewritten to make a mismatch disappear.

## Observed implementation

The [controller](../../scripts/hosted.py) uses Python's standard library and Docker CLI. It reuses the [configuration generator](../../scripts/configure-hosted.ts), existing owner/migration commands, [backup](../../scripts/backup.ts) and [restore](../../scripts/restore.ts). The [storage guard](../../scripts/lib/backup-storage.ts) checks Linux mount information and a registered marker; the [verification CLI](../../scripts/verify-backup.ts) authenticates archives without modifying a database. Runtime application permissions remain restricted. No new database table or migration is required by this tooling.

The shared [isolated runner](../../scripts/hosted_rehearsal.py) restores the selected authenticated archive, uses retained migration checks and existing instance/domain validators, and verifies health plus a newly recorded paused worker. No public API or training validation rules are added to host infrastructure. Operation format 2 stores phase intent, attempt results, timings and recovery/image references; status reads it without taking the operation lock. Completed and failed records remain in private operator state.

Image installation resolves a version/digest once and records the local ID and portable registry digest before activation. Source installation still builds an immutable local image. Resume uses the pinned identity, not a moved tag. Build-time metadata owns the source fingerprint and composition; backups authenticate that identity and reject source drift. Local source-only backups are also supported; recovering them builds their authenticated source and requires valid image metadata before activation. Rendered Compose state is private. Existing manual deployments retain their advanced runbooks and may explicitly adopt a supported layout. Fresh installation never attaches to them automatically. The user must include reviewed personal-plugin source and retained migration files in a custom candidate image. Changing a custom/older build to a registry image, changing repository, or dropping enabled plugins needs explicit acknowledgement before maintenance. The acknowledgement never bypasses retained migrations.

## Constraints and verification limits

New image builds and matching source archives exclude private environment/key files, exports, backups and generated state recursively, including inside plugins. Exact `.env.example` files and required source remain included. Publication, archive and build-stage/runtime image tests share synthetic path fixtures; archive formats and existing artifacts are unchanged.

Owner passwords use versioned scrypt parameters (N=65536, r=8, p=2; 16-byte salt, 64-byte derived key). Legacy hashes upgrade only after successful login, atomically with session creation. Two concurrent web checks bound memory; console recovery takes precedence over stale login verification. Runtime cannot directly edit the owner table; its one-time upgrade permission is defined in [ADR 010](../decisions/010-runtime-password-upgrade.md). Credential encryption accepts only canonical three-part base64 envelopes with 12-byte IVs and 16-byte GCM tags; existing valid ciphertext remains readable. Upgrade refreshes runtime permissions, and rollback requires the matched pre-upgrade backup.

Hosted images must declare application `athlete-panel` and hosted protocol 1 in `.athlete-panel-release.json`. Missing or unrelated metadata is rejected before activation. Backup storage uses `.athlete-panel-storage-id`; archives use the `ATHLETE-PANEL-BACKUP-1` envelope, and unsupported envelopes fail verification before any database restore. Daily retention only prunes recognized `athlete-panel-daily-` archives.

The primary hosted environment is Linux with Docker Compose, Buildx and Python 3.10+. Remote filesystem verification supports NFS/NFS4, CIFS/SMB3 and SSHFS. An explicit synthetic policy is available to the imported rehearsal only and is additionally restricted by a loopback origin and `_test` database in the container guard. There is no public CLI bypass for hosted remote-storage verification.

Public DNS/CA renewal, actual remote filesystem behavior, remote retention and restore after losing a physical server require operator acceptance. Source rebuilds still depend on available base images/package registries; retained local images and registry digests reduce rebuild dependence but do not replace a disaster rehearsal. No official registry/bundle is published by this implementation. Finish pending older-controller operations with their original controller before upgrading tooling. PostgreSQL major upgrades and automatic data cleanup are excluded.

Commands are canonical in [development](../development.md#private-server-installation). Individual checks, failures and outcomes belong in the [execution record](../plans/mvp-execution.md), separately from real deployment.
