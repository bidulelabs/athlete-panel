# Feature: reviewed external-agent training

## Purpose and scope

Let an external local harness read selected athlete context and propose pending training edits while the owner retains control. Athlete Panel runs no model or chat orchestration. Completion, links, athlete settings, injuries, secrets, activation, deployment and provider changes are outside agent mutation scope.

The [Garmin sport planning specification](garmin-sport-planning.md) extends structured context with sport groups/subgroups, rest, elevation and exercises. Notes-disabled grants redact exercise instructions and completion notes as well as existing narrative, and cannot duplicate or replace hidden instructions.

## Intended behavior

Specification status: approved. Authority: owner implementation request dated 2026-10-24, P6/R3–R4 and T6, preserved in the [execution record](../plans/mvp-execution.md).

On 2026-10-24 the owner additionally requested CLI connection with browser approval so tokens do not need to be copied manually. The owner approves a short-lived revocable grant with explicit date bounds and optional ordinary notes. The CLI stores the token in a private local file and never prints it. Exports include preferences/goals/zones, relevant training, injuries, activities and health within the selected range. Private plan descriptions, workout and interval notes, completion reasons, calendar notes, and event/injury notes are excluded by default. Relevant injury descriptions and profile goals remain explicit shared context. Secrets, operational settings, raw provider payloads and GPS are never exported. The owner sees categories before granting; the chosen harness may send this context to its model service.

Health in the context is daily for the last seven days only: today in the profile timezone and the six days before, within the grant. Earlier grant days are summarized in `healthWeeks`, one entry per calendar week clipped to the grant and to the day before the daily list, starting on Sunday when the profile prefers it and on Monday otherwise (the server has no browser locale for `auto`). Each entry lists `from`, `to`, the calendar `days` it covers and, for every health metric, the rounded `average` with the `days` that have a known value. A metric without a value that week is `{ "average": null, "days": 0 }`, never zero. Each account's latest correction for a day and metric replaces its earlier records, including a correction to unknown, with the calendar's revision rules; a day two Garmin accounts both still recorded is then left out. The `contextDigest` and the stored review snapshot still cover every daily record behind the averages, so a changed earlier day still requires owner review, and the digest does not change when a day leaves the daily list. Proposals stored before this summary keep their digest and snapshot and are reviewed as before. The hourly Garmin sync rewrites only the last seven days, which stay daily.

The agent reads a context digest, then submits typed commands, a summary and an idempotency key. Commands follow `agentCommandSchema`, the plan, workout, note and permitted race/goal creation actions an agent may propose; its generated JSON Schema (`agentCommands` in the [contract reference](../reference/contracts.json)) gives field units and meaning, as requested in [issue 37](https://github.com/bidulelabs/athlete-panel/issues/37). Any other action is refused before the context check with `400 validation`, listing the allowed actions under `commands.N.action`. Source records as well as resulting changes must be within the grant: copying an excluded source into an allowed date is forbidden. A full-plan operation needs access to all affected children.

The server validates and expands the entire batch before storing it. The UI presents before/after changes, derived dates and ordering effects. The Proposals tab lists pending proposals and groups applied and rejected proposals in a collapsible Past proposals section. See the [changelog](../changelog.md) for release availability. Proposals expire seven days after submission, independently of agent access expiry; reads/submissions still require active access and revocation still blocks owner application. New proposals store a versioned snapshot of the same permitted bounded context, preserving note exclusions. An owner-only review operation loads contextual differences and mutation conflicts on demand. Context-only changes permit renewed owner acknowledgement when domain validation, scope, revisions and the exact expanded diff still match. Application rechecks these conditions, the immutable digest and the reviewed current-context digest in one transaction. A further context change returns 409 and clears acknowledgement; changed edits require replacement. Legacy proposals without snapshots require replacement when context changes. There are no partial writes. See [ADR 009](../decisions/009-durable-proposal-review.md).

Retries with the same idempotency key and content return the original result. Reusing a key for different content conflicts; a proposal cannot be applied twice with different keys. Audit snapshots and results commit with domain writes.

Whole-batch undo checks every affected current entity against its recorded after-state. Any later edit rejects the whole undo, as does a restore that would move a workout or note added later, leave one without its plan, or give a later workout's position in its day to a restored one. Edits of other records in the same plan do not block it. Deleted state remains recoverable; restored entities receive higher revisions and deleted UUIDs cannot be recycled. Undo is another audit event. It does not reverse provider synchronization, migrations or external actions.

### Race and goal proposals

Specification status: approved. Authority: the owner's 2026-11-08 implementation request and default-on correction, preserved in the [execution record](../plans/agent-event-creation.md#authority-and-scope). [ADR 020](../decisions/020-agent-event-creation.md) records permission and compatibility choices.

New browser planning approvals show **Allow proposals to create races and goals**, checked by default, beneath the planning controls. The owner can uncheck it before approval. It is absent for historical-only access. The summary, connected-agent details and CLI receipt describe the actual permission. Modern planning scopes carry optional `allowEventCreation`; only explicit true permits creation. Omitted fields remain omitted when parsing stored scopes and snapshots, so legacy and existing modern grants retain their exact authority and existing proposals remain reviewable. A new owner-approved connection is required to gain permission.

Agents may propose `event.create` with a title, exact floating date, explicit `race` or `goal` kind, optional ID and permitted notes. Events use the existing inclusive planning dates and notes permission. Creation may be the sole proposal command or accompany plans/workouts in one atomic proposal. Event updates/deletions and `other` event creation remain owner-only. The Training engine validates the agent kind restriction; Agent Bridge checks grant permission, dates, notes and creation-only changes at submission and review/application. No model, event-to-plan association, new endpoint or storage migration is introduced.

An event with the same date and title (trimmed, internal whitespace collapsed, case-insensitive and Unicode NFC-normalized) blocks an agent creation regardless of kind. Canonically equivalent accented titles compare equally; accents remain significant and stored titles are preserved. The check covers existing events and the same proposal, and runs under the domain lock again before application. A newly introduced duplicate requires a replacement proposal; acknowledging changed context cannot override it. Manual event behavior is unchanged. Similar but differently named targets remain an agent clarification concern rather than a fuzzy server rule.

The coaching/planning skills use clear intent to prepare for a named race or dated goal; registration is not required. They check permitted existing events, clarify tentative intent, missing dates or ambiguous matches, and never invent dates. Missing permission/date coverage is reported while independently authorized training work continues. Incomplete visibility is described as “not found in the shared context,” not proof of calendar absence. The proposal summary names the creation and target date. Submission remains pending, without calendar writes.

Review lists the event's creation action, type, title, date and expandable fields. Week/month grouping and both proposal-list metadata and opened date bounds read event record dates without rewriting stored diffs. Events appear in the ordinary calendar after application. The existing audit, seven-day proposal lifetime, revocation, idempotency, atomic application and whole-batch undo apply, including an undo conflict when a later owner edit changes the event.

### Activity and health imports during planning

The owner approved [issue #68](https://github.com/bidulelabs/athlete-panel/issues/68) on 2026-11-04. Each planning read saves the bounded, note-redacted data behind the returned digest. Submission requires a digest this grant read. If only activities or health records in the planning period have changed, the server can accept a pending proposal. It validates the commands against current training and keeps the original read as the proposal’s baseline. Changes to the profile, plans, workouts, notes, events or injuries require a new read. This includes a Garmin correction that updates a linked workout.

Owner review lists the differences since the agent’s read, including changes before submission. The owner must acknowledge those differences before applying the draft. A further change requires another review. Records solely in the separate history window do not affect the planning digest. The temporary copy belongs to the grant. Revocation removes it immediately and the worker removes expired grants’ copies on its next cleanup. Each pending proposal keeps its own baseline for its existing lifetime.

### Adaptive coaching clarification

Requirement source: the owner approved the adaptive clarification improvement with “implement this” on 2026-10-25 in the current chat, following examples of next-week adjustments and a three-month trail-running program. Scope and verification are preserved in the [execution record](../plans/mvp-execution.md#adaptive-coaching-clarification--2026-10-25).

The training-planning entry point loads a companion coaching skill for program creation and workout adaptation. The agent first reads permitted context and prior user answers, then asks only unresolved questions whose answers materially affect the goal, training dose, schedule, feasibility or constraints. It does not repeat known information or impose a universal questionnaire. Weekly adjustments can proceed directly when context is sufficient. New multi-month programs clarify relevant missing goals/events, dates, training baseline, availability, terrain and constraints; a race is not required for a general-fitness goal.

Questions are brief and grouped, with choices when useful and a free-text answer available. They use the external harness's supported interface or ordinary chat, without requiring a special planning mode. Essential answers are awaited before dependent prescriptions or submission. Silence does not count as an answer; minor gaps can use explicit assumptions. A follow-up with partial answers asks only for remaining essential information. Explicit changes to preferences apply to the requested proposal without changing the athlete profile. Excluded private notes are not requested to fill an intake checklist.

After clarification the agent completes the requested duration and level of detail, validates the proposed changes and submits them through the existing scoped workflow. A three-month request is not silently reduced to two weeks or twelve weeks. Material scope/access conflicts are explained and resolved through the owner connection workflow before affected changes are submitted. Context is refreshed after a clarification pause. Coaching answers do not authorize application; the exact proposal is still reviewed/applied in Agent workspace.

This addition defines agent instructions, not a server-enforced questionnaire, new coaching algorithm, sport model or persisted intake record. Broader sport-reference libraries, numerical coaching-policy tooling and automatic recurring reviews remain outside this change.

## Observed implementation

Agent Bridge 2.2 adds [planning read storage](../../plugins/agent-bridge/migrations/002-planning-reads.sql) and [baseline selection](../../plugins/agent-bridge/planning-reads.ts). It preserves both versioned proposal formats. An in-flight draft whose read predates the migration needs one fresh read. Previously submitted proposals keep their original review behavior. See [ADR 019](../decisions/019-planning-read-baseline.md) and the [execution record](../plans/planning-read-baseline.md).

The [bridge service](../../plugins/agent-bridge/service.ts) implements bounded reads, source checks, immutable proposals and apply; [training service](../../plugins/training/service.ts) implements shared mutation, audit and undo. Owner endpoints use secure session cookies and same-origin checks. An owner-approved history grant exposes discovery, summaries, paginated records and context within the approved dates, categories and notes scope. A planning grant separately permits reading planning context and submitting a proposal within its dates. Only the signed-in owner can apply a proposal. Separate pairing endpoints enroll, poll, and cancel a connection; they cannot approve access. Grants are hashed at rest. Credential preflight rejects invalid requests before the domain lock; transactional checks remain authoritative for identity, expiry, revocation and scope. Unknown cancellation credentials remain a no-op. The [CLI](../../scripts/agent.ts) is a small HTTP adapter.

Legacy grants retain their original maximum of 121 inclusive days. New versioned grants independently support five-calendar-year historical review and one-calendar-year planning, with access lasting at most 24 hours. These capabilities do not broaden existing grants. The UI defaults to recent context plus upcoming training. The [connection service](../../plugins/agent-bridge/connections.ts) stores ten-minute pending requests in plugin-owned `agent_bridge.connections`. Enrollment is public and bounded to five requests per trusted client and 30 overall per ten minutes; it creates no grant. Host-owned counters persist across restarts, use database time and commit before enrollment work. Rejected clients do not spend the overall allowance. HTTP 429 responses include `Retry-After` seconds and matching `error.details.retryAfterSeconds`. Only the configured proxy supplies client identity; unproxied local use shares one bucket. Owner approval uses the existing authenticated, same-origin plugin operations. The CLI polls using an unguessable secret; only its hash is stored. On approval that hash becomes the ordinary scoped grant credential, with no raw secret exposed to the browser. Polling is paced, requests older than a day are cleaned on enrollment, and repeated identical approvals are idempotent. Tokens are never browser query parameters or terminal output. These are implementation limits, not an OAuth compatibility claim; the approval/polling design follows the separation described in [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628.html).

The [CLI implementation](../../scripts/lib/agent-client.ts) opens the default browser and provides an approval-link fallback. It atomically replaces private local configuration only after approval. Cancellation attempts server cleanup, and the owner can always disconnect access in the application. A lost network response or unavailable server can prevent immediate cancellation; no automatic renewal is provided. The owner chooses one, four or 24 hours in the browser. Manual stdin configuration remains an advanced compatibility path.

The [approval UI](../../plugins/agent-bridge/connections-client.tsx) preserves the connection through sign-in, shows the shared context and requires the owner to type the terminal code; the server never sends that code to the browser. Revoked/expired access requires fresh browser approval. Actual discovery/loading by each external harness remains a separate demonstration recorded in the execution record.

The [coaching skill](../../.agents/skills/athlete-panel-training-coaching/SKILL.md) implements the clarification instructions, and the [training-planning skill](../../.agents/skills/athlete-panel-training-planning/SKILL.md) links to it after context retrieval. Both have generated Claude discovery copies. Source inspection establishes the routing and instructions; it does not establish live model compliance. The CLI, proposal schema, server authorization and application UI are unchanged by this addition.

## Historical review and annual planning

Requirement source: the owner approved and requested implementation on 2026-10-31; choices and verification are in the [execution record](../plans/historical-agent-review.md). [ADR 016](../decisions/016-historical-agent-access.md) records the permission and consistency decision.

A version-2 grant contains optional independent `history` and `planning` capabilities, with at least one enabled. Historical categories are activities, health, training and current profile/context. Each capability has independent notes permission, off by default. The browser displays the combined access when both capabilities are selected. Historical-only connections cannot retrieve planning context or submit proposals. Five-year visibility cannot authorize proposal sources or results outside planning dates. Applying the exact reviewed proposal always requires the owner in Agent workspace.

Both dates are inclusive floating calendar dates. A range is allowed when its end is no later than the corresponding first/fifth anniversary of its start; February 29 clamps to February 28 in a non-leap anniversary year. Thus 2021-10-31–2026-10-31 is valid history and 2026-10-31–2027-10-31 is valid planning. Future dates are allowed. The resolved profile week boundary is captured at approval, including browser resolution of Automatic; subsequent profile changes do not rewrite that grant's boundary.

Legacy grants, saved CLI credentials and proposal snapshots retain their original meaning. New annual snapshots have version 3. Agent proposals support up to 1,500 commands and 4 MiB, while owner mutation requests retain their existing limits. An oversized annual proposal fails clearly without changing training or silently shortening/splitting the requested program. List responses carry required counts/date bounds and no `changes` field; opening a proposal returns a separate details contract with the exact diff, with large reviews collapsed by month and week. Seven-day proposal lifetime, revocation, stale-context review, idempotency, atomic apply and whole-batch undo remain unchanged.

### Historical read protocol

The bearer-authenticated bridge exposes history discovery, summary, records and current context operations. Public runtime schemas and generated references define their requests/results. Records support category, date, sport/subgroup and health-metric filters; incompatible filters are rejected. `recordId` requires an explicit record category. Coverage supports period filtering; `recordId` is rejected with an actionable validation error instead of being ignored. Prescription steps/exercises are separately paged parts. Missing older collections have unknown (omitted) counts, known empty arrays have zero counts, and unsupported collection shapes report `unsupportedFields` in the core record and a retrievable section diagnostic. Unsupported optional fields never erase other diagnostics. Default/max page sizes are 100/200 and each JSON response is at most 1 MiB. Source records remain in their owning plugins; the bridge does not load a historical workspace. Category-specific DTOs allow only relevant fields (a health reading has a metric/value, not workout distance). Owning database selections contain plain filters and positions, never review tokens or encrypted cursors. Required coverage evidence is not inferred from an older timestamp shape.

Discovery uses owning-plugin SQL count/min/max projections without materializing detail records. Training shares its dated selection with detail reads; plan/event reads omit the relative-schedule join. Discovery counts each available record once. Its date bounds include all permitted scheduled and performed dates, and the full overlapping extent of injury and import-coverage intervals. Bounds stay inside the requested dates and approved scope; an open injury ends at the selected end date for this metadata only. They describe available records/scan windows, not continuous measurement availability. The relevant date used for keyset ordering remains unchanged and need not be the last date represented by a record.

A review token captures permitted collection versions. Keyset cursors bind the review, grant, query, filters and page size. Ordinary records sort by relevant date and ID; prescription parts sort by ordinal; summaries by period/category/sport/source/metric. Every page revalidates access and source versions. Changes in any participating collection, even outside the requested period, return `history_changed`; discard earlier pages/results and restart discovery. There is no cross-request frozen database transaction or stored duplicate historical export. Authorization, dates and notes are checked independently for each request and embedded facts. Secrets, operational state, raw provider payloads and GPS have no historical export representation.

Historical requests use read-only READ COMMITTED transactions without the domain write lock. Fresh source versions, grant expiry/revocation and maintenance are rechecked before returning a result; a participating change during a scan rejects that response. Sanitized summary rows may be reused in process memory for up to five minutes, capped by access expiry, eight entries and 32 MiB of serialized rows. Keys include the grant, scope, versions and normalized query. Reuse never bypasses authorization or version checks. Cache misses, eviction and process restarts recompute the same result under the existing review; source changes still require explicit restart. Large uncached summaries retain the same bounded response semantics. See [ADR 017](../decisions/017-historical-read-reuse.md).

Following [ADR 018](../decisions/018-history-factual-invalidation.md), owning-schema counters ignore zero-row statements, identical writes and operational timestamp-only updates. Record identities, kinds, revisions, data and deletion state remain versioned. Garmin versions its historical coverage projection (stream/window, status, scan evidence and stable scan state), not live timestamps or operational counts/diagnostics that are absent from historical DTOs. A real change anywhere in a participating collection still invalidates the review. Bulk statements advance counters per changed event rather than per row; rollback restores the counter with the data, and nonempty truncation invalidates.

Profile context is explicitly current, not a record of past settings. Dated events/injuries are retrieved through records. Excluded notes include plan descriptions, calendar notes, workout/interval/exercise instructions and completion narrative; injury descriptions and profile goals retain their established explicit context meaning. Unknown legacy fields are never substituted with current profile assumptions; invalid optional fields have explicit diagnostics. Unsupported health metrics remain visible as excluded summary contributions with null aggregates and a query for their supporting records.

### Summary semantics and evidence

Monthly summaries are the default; weekly summaries use the grant's captured week boundary. Partial periods are clipped and labelled. Every emitted `reference` and `detailReferences` query includes the exact response `reviewToken`, so forwarding it directly retains the review's context and returns `409 history_changed` after a participating correction. Cached aggregates remain token-free; references are bound to the current review before enforcing the serialized page budget. Recorded count, seconds, meters, elevation meters, active days and sessions per seven calendar days describe stored observations, not inferred inactivity or training load.

Planned volume follows scheduled dates; actuals follow provider/performed dates. Imported activities contribute once, linked workout copies contribute no additional actual volume, and non-skipped manual completions contribute separately. Potential overlapping manual sessions remain counted with a warning. Rest prescriptions do not contribute session volume. Planned completion counts and actual volume are separate measures. Unselected categories never contribute facts; response warnings identify comparisons unavailable because training or activity access was excluded.

Known measurement sums carry known/missing counts; absent measurements are null, including an entirely unmeasured total. Known zero is retained. Health corrections resolve by source stream/account/day/metric, then highest revision, measured timestamp and ID, including corrections to null. Daily means/minima/maxima use known corrected values; only steps receive an additive total. Separate source series preserve conflicting streams and accounts and report ambiguity, unknown days and provenance uncertainty. Existing provider scores remain provider scores; no diagnosis or recovery/load score is created.

Import scan coverage is separate from available measurements. Overlapping windows count each scanned calendar day once. Failed/unavailable windows and unscanned dates remain visible. Window record counts are not prorated into partial periods. Successful scanning does not establish that the provider supplied every measurement.

New historical coverage records expose `hasCompletedScan` instead of the live last-scan timestamp. An in-progress repeat scan retains the prior completed scan state until its evidence changes; first scans without completed evidence remain in progress. Failed/unavailable states remain visible even when a window was scanned previously. This preserves identical results during an unchanged rescan while Garmin's owner-facing status continues updating its actual last-scan time. `hasCompletedScan` is required in the final pre-release coverage contract. Intermediate branch-only timestamp exports must be regenerated; the owner explicitly authorized removing that compatibility path.

### Simpler assistant workflow

Authority: the owner requested implementation of the six simplifications discussed in this chat on 2026-10-31, using Impeccable for UI/UX refinement. This changes presentation and local CLI orchestration, not server permissions or stored proposals.

One “Training assistant” setup asks how much history to read, then whether it may suggest training changes. History presets cover the last four weeks (default), one year or five years, plus Custom dates and None. Suggestions default to “Yes, for me to review” with a separate next-two-weeks period; “No, analysis only” omits planning authority entirely. Other proposal presets cover the next twelve weeks or calendar year. Exact date fields appear only for Custom dates; the always-visible approval summary includes the actual inclusive dates for every preset.

The last-four-weeks preset means today minus 27 days through today. Next two/twelve weeks means today through today plus 13/83 days, so proposal presets never authorize past edits. Calendar-year presets retain inclusive anniversaries and leap-day handling. On February 29, a backward history preset starts March 1 in the non-leap start year so its forward anniversary still includes today. Custom dates may include past or future dates within the capability's limit. Changing the history selection never changes proposal dates. Existing connections retain their approved scopes; these defaults apply only to fresh browser approvals.

One “Customize shared data” disclosure contains history categories and independent history/proposal note permissions, off by default. The summary explicitly says that planning also reads existing profile, goals, availability, zones, training, events, injuries, activities and health within its proposal dates. A historical category exclusion does not exclude the same category from separately approved planning dates. Current profile/settings remain current context. Historical reads cannot authorize copying or changing a source outside the proposal scope. Analysis-only cannot submit proposals, and no-history plus analysis-only is rejected with an actionable message. The resolved week start, expiry and mandatory owner review/application remain visible.

This is a browser composition of the existing version-2 capabilities, not a combined server permission. The CLI reads prior facts through the historical commands and proposed-date records through planning context, retaining the latter's digest for submission. No new contract, migration or change to saved proposal snapshots is introduced.

The CLI defaults bare `history` to monthly summaries. It automatically discovers and reuses a protected review sidecar bound to the instance/credential, while explicit review/cursor files remain available. Summary and record exports with an output file fetch all pages atomically by default; `--page` preserves single-page behavior. Stale reviews require an explicit restart of the analysis; no automatic retry silently mixes versions. Each request retains the existing server authorization and bounded response checks. Canonical commands are in [development](../development.md#historical-review-and-annual-planning-commands).

The canonical training-planning skill explicitly retrieves approved recent weekly history before choosing or adapting training. Planning `health` and `healthWeeks` remain restricted to proposal dates. Existing broader/legacy scopes retain their daily/weekly behavior. Proposal review starts with affected date bounds (including both ends of moves and before/after plan start dates), sports and added/changed/deleted record counts. Every edit remains accessible and the whole proposal still requires owner acknowledgement and atomic application.
